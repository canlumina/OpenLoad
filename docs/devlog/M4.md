## 2. M4-1: SHA-256 摘要

**commit**: `5f685ed`

`OPENLOAD_ENABLE_SHA256` 配置位 M1 阶段就预留, image header 里
`firmware_sha256[16]` 字段也已留位. 本次端到端打通.

### 2.1 算法选型

`third_party/sha256/` vendor in Brad Conte 公有领域实现:
- ~5.3KB 源, 单文件 (sha256.c + sha256.h)
- 标准 SHA-256 (FIPS 180-2), 跟 Python `hashlib` / OpenSSL 等任意实现兼容
- `SHA256_CTX` 流式 init/update/final, 适合 SPI flash 流式校验

不选自实现: SHA-256 标准实现 ~300 行, 自己写没意义且容易出 endian bug.

### 2.2 hdr 字段设计取舍

`firmware_sha256[16]` 仅存 SHA-256 前 16 字节 (128-bit 截断). 取舍:

| 选项 | 抗碰撞 | hdr 占用 |
|---|---|---|
| 完整 SHA-256 (32B) | 256-bit | hdr -16B 给 ed25519 留位 → 不够 |
| 截断 16B (本方案) | 128-bit | 节省 16B, 跟 aes_iv 平起平坐 |
| 不放 hdr (运行时算+签名) | N/A | 0 |

128-bit 抗碰撞对固件更新场景充分 (攻击者要构造 SHA collision 才能绕过,
比破 AES-128 还难). 节省的 16B 留给 ed25519 不放 hdr 的 sig — 见 M4-2.

### 2.3 流式校验

`sha256_partition_full()` 从分区 offset 起按 128B chunk 流式算, 不缓存
整个 payload — 跟 CRC32 / AES 解密路径一致, 16KB+ 固件不占大量 RAM.

### 2.4 渐进启用

`hdr.firmware_sha256` 全 0 时跳过 SHA 校验:
- 让老固件 (无 SHA 字段) 仍能通过 `ol_image_verify`
- 新固件可逐步上 SHA (image_tool 默认开, `--no-sha256` 可关)

### 2.5 跟 AES 联动

加密 image 时 SHA 也是 *明文* SHA, 跟 `firmware_crc32` 同语义.
`install_ex` 加密分支:
1. 解密 payload 到 target
2. 拷 hdr 到 target, 清 ENCRYPTED + aes_iv (SHA 字段原样保留)
3. `ol_image_verify(target)` — 此时 target 是明文 image, SHA 校验自动跑

target hdr 上始终是 SHA 正确的明文 image, boot/jump 走标准 verify 链.

### 2.6 host 跨实现 self-test

`tools/host_test_sha.c` 把设备同款 Brad Conte sha256.c 编进 host 程序,
跟 Python `hashlib` 算同一个 app.bin 比对:

```
hashlib   : 0594475daa188bbd078e45b33e014c4a...
Brad Conte: 0594475daa188bbd078e45b33e014c4a... (match)
```

跨实现算法对齐确认, 设备烧测一次过.

### 2.7 端到端

- 正向: `app-enc-v2-sha.bin` (AES + SHA) → `decrypt` → `verify target` (含 SHA) → install ok
- 反向: `firmware_sha256[0]` flip 1 bit + 重算 hdr_crc32 → 设备 `[E] verify: image sha256` → M3-2 联动 auto rollback ok

## 3. M4-2: Ed25519 签名验证

**commit**: `c4d5c4a`

### 3.1 算法选型

`third_party/tweetnacl/` vendor in TweetNaCl (Public Domain):
- 16KB 源, 单文件 (tweetnacl.c + tweetnacl.h)
- 是 F103 64KB 区间唯一能塞下的标准 Ed25519 实现
- 备选: micro-ecc (~7KB 但支持多曲线, 杀鸡牛刀) / ed25519-donna (~10KB+ 太大)

TweetNaCl 一个文件包含 box/secretbox/sign/auth/stream/hash 全套, 我们只用
crypto_sign_open. linker -gc-sections 把未用 primitives 剔除, 实际占用 ~4.5KB.

### 3.2 randombytes stub

TweetNaCl 要求外部提供 `randombytes`, 仅 keypair/sign 路径调. verify 路径
完全不调. 提供死循环 stub:
- 正常 verify 流程永远不触发
- 万一 GC 没干净或未来配置变化拉进 keypair 代码, 死循环让看门狗复位
- 比静默返回 0 安全 (避免假装"随机" key 派生)

### 3.3 签什么, 放哪

**签名内容 = SHA-256(plain_payload) 摘要 32 字节**:
- 跟 M4-1 SHA 自然联动, 不重复算 hash
- ed25519 内部还会再算一次 SHA-512(msg), 32B msg 比 16KB payload 快得多
- 设备 verify: 用流式 SHA-256 算出完整 32B → `crypto_sign_open(pubkey, sha32, sig)`

为此把 M4-1 的 `sha256_partition_first16` 重构成 `sha256_partition_full`,
出完整 32B. 前 16B 比对 `hdr.firmware_sha256` (M4-1 自校验), 完整 32B 给
ed25519 verify 用. 一次 SHA 算出, 两个用途.

**签名位置 = image 末尾追加 64 字节**:
- `image = [hdr 64B] [payload] [sig 64B (当 SIGNED)]`
- `hdr.flags |= OL_IMG_F_SIGNED`, `firmware_size` 仍是 payload 长度
- 不破坏 hdr 64B 布局, 不 bump `OL_IMAGE_FMT_VER`
- 老 image (无 SIGNED) 仍能通过, 跟 SHA 同样渐进启用

### 3.4 加密 + 签名叠加

加密 image 的 sig **不参与 AES**, 是明文 trailer:

```
image_tool 输出:
  [hdr (含 ENCRYPTED + SIGNED flag)]
  [AES_CTR(payload, key, iv)]
  [sig = ed25519_sign(SHA-256(plain_payload), seed)]   <-- 明文
```

设备 install_ex 加密分支:
1. 解密 payload 流式落 target, 算 plain CRC32 (M3-4)
2. CRC 比对
3. **拷 sig 64 字节从 staging 末尾到 target 末尾** (新增, 不解密)
4. 写 target hdr: 清 ENCRYPTED + aes_iv, **保留 SIGNED flag**, 重算 hdr_crc
5. `ol_image_verify(target)` — 此时 target 已是 [hdr(SIGNED, no ENC)][plain_payload][sig], 走 CRC + SHA + Ed25519 三层 verify

**SIGNED flag 必须保留** — 不然攻击者改 image_tool 不签名 + 改 ENCRYPTED 但
不动 SIGNED, 设备 verify 跳过签名分支, 等于绕过. install 解密时保留 SIGNED
让 ed25519 校验必走.

### 3.5 pubkey 部署

`OPENLOAD_ED25519_PUBKEY_BYTES` (32 字节 initializer list) 编进 bootloader
常量. 跟 M3-4 AES key 同模式:
- 默认全 0 让构建不挂, 但全 0 pubkey verify 永远不会通过
- 项目实际部署在 `openload_config.h` 填真实 pubkey
- M5+ 可叠 OTP/RDP 把 pubkey 锁起来 (防 dump bootloader 反推)

但注意: **pubkey 不需要保密** (跟 AES key 性质不同). 攻击者拿到 pubkey
也无法伪造签名 (除非破 ed25519). 但能改 pubkey 来绕过 → 这才是要防的.
所以 RDP 是有意义的 (防写, 不需要防读).

### 3.6 host 跨实现 self-test

`tools/host_test_ed25519.c` 把设备同款 tweetnacl.c 编进 host 程序, verify
pycryptodome 签的 sig:

```
PC sign     : pycryptodome eddsa rfc8032 mode (RFC 8032 标准)
Device verify (host 测): tweetnacl crypto_sign_open
=> rc=0, mlen=32  (OK)
```

跨实现算法对齐确认 — Ed25519 / RFC 8032 是标准化算法, 但两个实现间的
endian 处理 / sig 编码偶尔会翻车, 这一步必做.

### 3.7 demo keypair 工具

`tools/gen_demo_ed25519.py` 用固定 seed (`"OpenLoad-demo-ed25519-seed-v1!!!"`)
派生确定性 demo keypair, 用于测试. 项目实际部署必须用真随机 seed.

### 3.8 端到端

- 正向: `app-enc-v3-sig.bin` (AES + SHA + Ed25519 三层叠加) → `verify target` → install ok
- 反向 (跳, 正向 + host self-test 算法对齐已确认)

## 4. M4-3 / M4-4 F103 平台边界

### 4.1 M4-3 Dual Bank 硬伤

F103 没硬件 dual bank (F4 才有). 软件模拟方案不可行:

| 方案 | 问题 |
|---|---|
| 编两份 app, 分别链 slot_a / slot_b 地址 | 用户工程要双链, 体验糟; 升级时还要选对应槽的 image |
| Vector table relocation + 运行时拷贝到固定地址 | 等于当前 STAGING+BACKUP 策略, 不是真 dual bank, 仍有擦写窗口 |
| Position-independent code | Cortex-M 不擅长 PIC, 实际生态没人这么做 |

**结论**: F103 上做"真 dual bank" (无擦写窗口 + 直接跑非活跃槽) 几乎不可能.
转 F4/F7 (双 bank flash 硬件支持) 才是合理路径.

当前 backup/rollback 策略已经覆盖了 dual bank 想解决的 "升级中断恢复"
痛点, 只是不能在升级过程中保持服务连续. 对 bootloader 场景一般够用 —
升级期间设备本来就要重启.

### 4.2 M4-4 HTTPS 硬伤

mbedtls 最小化:
- 无 ECDHE, 仅 RSA + AES-128 → 40-50KB .text
- 加 ECDHE/X25519 → 55-65KB
- 加证书链验证 → 70KB+

F103 bootloader 区 64KB, 当前已占 74%, 剩 ~16KB. 装不下 mbedtls 任何裁剪版.

**结论**: HTTPS 需要至少 128KB ROM 区间, 必须切 F4/F7. 加 mbedtls 后预计 bootloader 总占用 ~110KB.

替代方案 (M5+ 探索):
- 应用层加密 OTA (AES-CTR 已经够大多数威胁模型, M3-4 已有)
- DTLS-PSK (~30KB, 不需要证书链, 但需要预置 PSK)
- COSE/CBOR 签名 (~10KB, 跟 ed25519 联动, 但需要 IoT Hub 类基础设施)

## 5. 度量

| 指标 | M3 收尾 | M4-1 收尾 | M4-2 收尾 | 增量 |
|---|---|---|---|---|
| `.text` | 40.5 KB | 41.5 KB | 48.2 KB | +7.7 KB |
| FLASH (64KB 区) 占用 | 62.1% | 63.9% | 74.0% | +11.9% |
| RAM 占用 | 12.5 KB | 12.5 KB | 12.5 KB | 0 |
| 剩余 FLASH | 24.2 KB | 23.4 KB | 16.6 KB | -7.6 KB |

M4 各项体积:

| 任务 | FLASH 增量 | 备注 |
|---|---|---|
| M4-1 SHA-256 | +1.8% (~1.2KB) | Brad Conte 实现 + image.c 集成 |
| M4-2 Ed25519 | +10.0% (~6.5KB) | tweetnacl ed25519 + SHA-512 内部 + verify 路径 |

**F103 64KB bootloader 区剩 16.6KB**: 还能塞下 USB DFU receiver / CAN ISP 之类
小型 receiver, 但塞不下 mbedtls 或重型协议栈.

## 6. 完整安全栈 (M1 → M4)

| 维度 | 实现 | 来源 |
|---|---|---|
| 传输完整性 | CRC32 (payload + header) | M1 |
| 跨型号保护 | board_id 比较 | M1 |
| 防回滚 | firmware_version 比较 | M3-1 |
| 防误刷 | `install ... force` 二次确认 | M3-1 |
| 失败恢复 | backup/rollback 三处自愈 | M3-2 |
| 物理攻击防护 | CLI password + 失败锁定 + oplog | M3-3 + M2-13 |
| 机密性 | AES-128-CTR | M3-4 |
| 抗碰撞摘要 | SHA-256 (128b 截断) | M4-1 |
| 真实性 / 抗篡改 | Ed25519(SHA-256, sig, pubkey) | M4-2 |
| 可观测性 | oplog 持久化 ERR/WRN, 跨复位累积 | M2-13 |

**唯一缺失**: 信任根 (Root of Trust). 当前 pubkey/AES key 在 bootloader 二进制里,
攻击者能 dump bootloader 改 pubkey 绕过签名. M5+ 用 STM32 RDP (Read Protection)
+ option byte 写保护可以补上这一环.

## 7. 关键设计取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| SHA 截断位数 | 128b (16B) | 抗碰撞充分, 节省 hdr 16B; 完整 32B SHA 仅运行时用 |
| SHA 启用条件 | hdr.firmware_sha256 非全 0 | 老 image 兼容, 渐进启用 |
| Ed25519 签什么 | SHA-256(payload) 摘要 | 跟 M4-1 联动, 不重复算 hash |
| Ed25519 sig 位置 | image 末尾追加 64B | 不破坏 hdr 兼容性, 渐进启用 |
| sig 是否参与 AES | 否, 明文 trailer | 设备解密时 sig 直接拷, 不走 AES 路径; 简化流程 |
| install 解密时 SIGNED flag | 保留 (不清) | 防绕过 — 改 ENCRYPTED + 不改 SIGNED 会让 verify 漏签名 |
| Ed25519 库 | TweetNaCl | 16KB 单文件 public domain, F103 64KB 区唯一塞下的标准实现 |
| randombytes | 死循环 stub | verify 不调用; 误用立刻看门狗复位, 比静默假装随机安全 |
| pubkey 部署 | 编进 bootloader 常量 | 跟 M3-4 AES key 同模式; M5+ 叠 RDP |
| Python 端 ed25519 | pycryptodome eddsa rfc8032 | 已有依赖 (M3-4 装的), 不新增 |
| dual bank | F103 上不做 | 硬件不支持; backup/rollback 已覆盖中断恢复痛点 |
| HTTPS | F103 上不做 | mbedtls 40KB+ 装不下; 应用层加密 (M3-4) + 签名 (M4-2) 覆盖大多数威胁模型 |

## 8. 遗留 → M5+

| 项 | 描述 |
|---|---|
| STM32F4 / F7 port | 大 ROM 平台, 解锁 dual bank + HTTPS 路径 |
| RDP / OTP key 锁定 | 信任根: 用 STM32 RDP Level 2 + option byte 写保护, 防 bootloader dump 反推 pubkey |
