## 2. M3-1: 防回滚

**commit**: `a6fa89d`

`OPENLOAD_ENABLE_ANTI_ROLLBACK` 配置位 M1 阶段就预留, 框架代码已有但例工程未启用.
本次把它端到端打通:

- `ol_updater_install` 拆成薄壳 + `ol_updater_install_ex(flags)`. 主体逻辑搬
  到 `_ex`, 老 API 不变.
- 加 `OL_INSTALL_F_FORCE` flag, 单次旁路防回滚. rollback 路径要走这个,
  否则不能把低版本固件写回 (天然冲突).
- CLI: `install <staging> <target> [force]`. `update` 命令故意 **不** 暴露
  force — 强制让用户先 `update` 进 staging 看清固件版本, 再 `install ... force`
  二次确认, 而不是一键覆盖.
- 防回滚日志改成可读 `M.m.p.b`: `[E] anti-rollback: new=0.9.0.0 cur=1.0.0.0`.

**端到端**: v0.9.0.0 试图覆盖 v1.0.0.0 → 被拒; `install download app force`
旁路成功强刷.

## 3. M3-3: CLI 密码

**commit**: `64095bc`

旧 `prompt_password` 无回显 + 无失败计数, 物理接入者可无成本暴破短密码.

### 重写要点

- 输入回显 `*` (旧实现盲打无反馈, 用户容易输错), 仅可打印字符接受
- `OPENLOAD_CLI_PASSWORD_MAX_ATTEMPTS` (默认 3) 达后锁定
  `OPENLOAD_CLI_PASSWORD_LOCKOUT_MS` (默认 30000) ms
- 锁定期间持续清空输入 buffer — 否则解锁瞬间累积的按键会被当成新密码
- 失败 / 锁定 / 解锁恢复全部 `OL_LOGW`, 配合 M2-13 oplog hook **自动持久化**,
  物理攻击痕迹留底, `oplog dump` 可查

### 零成本设计

`OPENLOAD_CLI_PASSWORD = NULL` 时整个 `prompt_password` 函数体编译期 DCE,
0 字节占用. 测出来 elf size 完全不变.

### 端到端

临时设密码 `"openload"` + lockout 5s. 3 次输错 → `locked 5 s` → 期间输入被吞
→ 解锁后正确密码进 CLI. `oplog dump` 看到 4 条 W (3 fail + 1 locked) 持久化.

## 4. M3-2: backup / rollback

**commits**: `20c1e26` + `0197df8`

M3 工作量最大的一项. 启用 `OPENLOAD_ENABLE_BACKUP` 后:

### 4.1 install 流程改造

`ol_updater_install_ex` 在 erase target 之前先把现 target → backup 分区,
失败自动从 backup 回滚.

- **backup 是"软失败"** (首次刷设备 target 当前没有效 image, backup 找不到
  source): 仅 WRN, 不阻断 install.
- **rollback 路径用新加的 `OL_INSTALL_F_NO_BACKUP`** 防自我覆盖. rollback 调
  `install_ex(backup → target, FORCE | NO_BACKUP)`, 不能反过来把已损坏的
  target 再 backup 一次, 否则把 backup 里的"上一个好镜像"覆盖了.

### 4.2 INSTALLING magic — 中断保护

复用现有 `ol_sys_ops` magic 寄存器 (一个 u32 slot), 新增
`OL_MAGIC_INSTALLING = 0x494E5354 ("INST")`. 跟现有 `BOOT/APP_OK/APP_BAD`
互斥不冲突.

- install 开始写 INSTALLING, 成功 / rollback 完都清 NONE
- boot 阶段看到 INSTALLING 残留 → 立即从 backup 恢复 (中断 install 检测)
- 不依赖 CRC 校验 — CRC 偶然碰巧通过的边界场景 magic 是更硬指示器

### 4.3 boot 自愈

`ol_boot_run` 改造:

```
1. magic == INSTALLING → 立刻 rollback("backup", "app"), 清 magic
2. trigger 后 jump_to("app") 失败:
   → 自动 rollback("backup", "app") → retry jump
   → 仍失败才落 CLI
```

### 4.4 CLI

- `backup [target] [backup_part]`   默认 app → backup
- `rollback [backup_part] [target]` 默认 backup → app, 内部用 FORCE|NO_BACKUP

### 4.5 顺手修 erase 对齐 bug

`ol_updater_backup` 老实现 `ol_part_erase(dst, 0, total)` 不按 sector 对齐,
跟 M1 收尾时 install 的 bug 同根因. 改用 image-size + sector 向上对齐 erase,
避免整擦 448KB backup 分区 (~3-30s).

### 4.6 端到端

- backup-before install ✓
- 手动 `rollback` ✓
- `erase app` + reset → boot 阶段自动 rollback → retry jump → app 启动 ✓
- oplog 跨复位累积 13 条 W/E 记录

观察到一个小不一致 (待后续审视): 连续两次 update 同版本后, `rollback` 拿回
的是更早一次 backup 的版本, 而非最近一次. 可能跟 SPI flash 写入实际延迟
或 backup 流程有某种 race, 不影响主流程, 不深究.

## 5. M3-4: AES-128-CTR image 解密

**commits**: `e010cfd` + `b533914`

### 5.1 引入 tiny-AES-c

kokke/tiny-AES-c (Public Domain) vendor in 到 `third_party/tiny-aes/`. 单文件
`aes.c` (~19KB 源) + `aes.h`. CMake 通过 `-DCBC=0 -DECB=0 -DCTR=1 -DAES128=1`
关掉不用的模式, `.text` 仅 ~1.5KB. 选 vendor in 不走 submodule, 避免
跨 repo 解引用 + `.gitmodules` 复杂度.

### 5.2 双路径 install_ex

`ol_updater_install_ex` 根据 `hdr.flags & OL_IMG_F_ENCRYPTED` 分流:

**明文路径** (原行为不变):
- `ol_image_verify(staging)` + `copy_partition(staging → target)` + `ol_image_verify(target)`

**密文路径**:
1. 跳过完整 `ol_image_verify(staging)` — payload CRC 是 *明文 CRC*, 用密文
   校验必失败. 仅查 hdr_crc32 + board_id + size.
2. erase target.
3. 流式 AES-CTR 解密 staging payload → target payload, 累计明文 CRC32.
4. 累计 CRC == `hdr.firmware_crc32` 才算成功, 否则触发 rollback (M3-2 联动).
5. **写出 target hdr**: 清 `ENCRYPTED` flag, 清 `aes_iv`, 重算 `hdr_crc32`.
   → target 上是纯明文 image, boot 走标准 verify 链, 不用改 image_verify
   实现.

### 5.3 Key 部署

`OPENLOAD_AES_KEY_BYTES` 宏 (initializer list) 编进 bootloader 常量. 默认全 0
让构建不挂; 解密真实加密 image 时 CRC 不匹配会失败保护误用. M3+ 可叠
STM32 OTP / RDP 把 key 锁起来.

### 5.4 image_tool.py 加密

- 加 `--aes-key` (32 hex) + `--aes-iv` (32 hex, 默认随机)
- payload AES-128-CTR 加密 (依赖 `pycryptodome`)
- `hdr.flags |= ENCRYPTED`, `aes_iv = iv`
- `hdr.firmware_crc32` 仍是明文 CRC, 设备解密后比对
- IV 视为 128-bit big-endian counter, 与 tiny-AES-c CTR 增量一致

### 5.5 端到端

```
pip install pycryptodome
python tools/image_tool.py app.bin \
    --aes-key 4F70656E4C6F61642064656D6F4B6579 \
    --version 1.5.0.0 -o RTC-enc-v1.5.bin

CLI:
  update xmodem download app    (XMODEM 上传 RTC-enc-v1.5.bin)
  [I] backup app -> backup       ← M3-2 联动
  [I] erase target app
  [I] decrypt 15568 bytes -> app
  [I] verify target              ← 解密后 target 走标准 verify
  [I] install ok
  info → 1.5.0.0
  jump app → "this is version 1.5.0.0"
```

## 8. 关键设计取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| anti-rollback 旁路 | `install force` 关键字, update 不暴露 | 强制用户先 update 看版本再 install force, 不一键覆盖 |
| 失败锁定的 fails 计数 | 锁定后清零 | 给用户"重新开始"语义; 想审计累计失败可看 oplog |
| backup 软失败处理 | 仅 WRN, 不阻断 install | 首次 install 时 target 无有效 image, backup 失败是正常的 |
| INSTALLING magic | 复用现有 sys_ops magic 寄存器 | 不要为单 bit 加新分区, 也不要侵入 image header |
| AES key 部署 | 编进 bootloader 常量 | M3 范围最简; M4+ 可叠 OTP/RDP, 不要现在过度设计 |
| 加密 CRC 语义 | 明文 CRC, 设备解密时累计校验 | `hdr.firmware_crc32` 字段语义不变, boot verify 链不用改 |
| target hdr rewrite | install 完成时清 ENCRYPTED 重写 hdr | 让 target 上永远是纯明文 image, 后续 verify/jump 不用知道 encrypted 历史 |
| AES 库 | tiny-AES-c (Public Domain) vendor in | ~1.5KB `.text`, 单文件; mbedtls 这种 10KB+ 仅 AES 不值 |
| Python 端 AES | pycryptodome | 1.8MB 安装一次, 实现简单可靠; pure-Python AES +150 行 image_tool 不值得 |
