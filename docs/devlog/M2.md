## 2. M2-10: YMODEM Receiver

**commit**: `13a0b56`

YMODEM 在 XMODEM-CRC 基础上加 block 0 文件信息头 (filename + size + ASCII space + ...). 状态机:

```
WAIT_HEADER     ← 发 'C', 等 block 0 (含文件信息)
WAIT_DATA       ← ACK 后, 收 block 1..N
WAIT_FINAL_HDR  ← 全 0 block 表示批次结束
```

CRC16-CCITT (XMODEM variant) 在模块内独立实现, 不依赖 xmodem.c 的版本, 模块解耦.

### 踩坑: SecureCRT YMODEM 卡 `CCCCCCCCCC`

SecureCRT 自带的 YMODEM 实现对端实测不发握手. 切到 **Tera Term** (File → Transfer → YMODEM → Send) 一次成功:

```
46 KB / 5 s ≈ 9 KB/s, 0 errors
```

**结论**: 文档里点名 Tera Term 是 YMODEM 推荐工具, SecureCRT 仅供 XMODEM.

## 3. M2-12: ESP8266 AT 桥接

**commit**: `5f21e37` (一个大 commit 含 12a/b/c/d 四个子任务)

### 12a: UART2 裸驱动

- PA2/PA3, DMA1_Ch6 RX circular (256B DMA buffer + 2048B ringbuf), Ch7 TX 阻塞.
- 直接编辑 CubeMX 生成的 `Core/Inc/usart.h` / `Core/Src/usart.c` / `dma.c` / `stm32f1xx_it.c` 加 USART2 分支. 不走重新生成路线避免重复手工调整.
- 不注册 ol_io_dev_t — UART2 是 ESP8266 专属内部通道, 不暴露给应用层.

### 12b: AT 引擎

`port_esp_at_send(cmd, timeout, resp_buf, buf_size)`:

- 命令尾自动追加 `\r\n`
- 16B 滑动尾部 buffer 做 `\r\nOK\r\n` / `\r\nERROR\r\n` / `\r\nFAIL\r\n` 后缀匹配, 不依赖完整响应缓冲
- 返回 `OL_OK` / `OL_E_AT_ERROR` / `OL_E_TIMEOUT`

适配单连接模式 (CIPMUX=0), 同时兼容 AT v1.2 / v2.x. 实测板上 ESP-01 是 Ai-Thinker v1.5.4.1 (即 AT v1.2.0.0), 与最初问询时回答的 "v2.x" 不符 — 用 `AT+GMR` 现场核对, 协议层无需改动.

### 12c: WiFi + TCP smoke

- `port_esp_wifi_join(ssid, pass)`: 先 `AT+CWMODE=1` (忽略已是 station 的 ERROR), 再 `AT+CWJAP`. 超时 20s — v1.2 实测偶尔到 15s.
- `port_esp_tcp_open/send/recv/close`: CIPSTART/CIPSEND/CIPCLOSE + `+IPD,<n>:<data>` 段头解析.

### 12d: net io_dev + wifi_cfg 持久化

将 TCP 操作封装到标准 `ol_io_ops_t` (`port_esp_net_open` → `port_esp_tcp_open` 等), 注册名 `"net"`. 协议层通过 `ol_io_dev_find("net")` 拿到设备, 不直接依赖 port_esp8266.h.

WiFi 凭据持久化到 W25Q64 `wifi_cfg` 分区 (4KB sector), 144B 记录:

```c
struct { uint32_t magic; uint32_t version; char ssid[64]; char pass[64];
         uint8_t reserved[4]; uint32_t crc32; }
```

CLI: `wifi join <ssid> <pass>` (自动保存) / `wifi load` (用上次凭据重连) / `wifi clear`.

## 4. M2-11: HTTP OTA Receiver

**commits**: `b057727` → `0e5cdfc` → `be22f8c` → `1731a69`

### 4.1 接口扩展 (commit `b057727`)

HTTP OTA 需要两件 XMODEM/YMODEM 没有的能力:
1. **传入 URL 参数** — 与 receiver 通用 `begin(io, dst)` 签名不兼容
2. **TCP 链路建立 / 断开** — 不能直接 `port_esp_tcp_open`, 否则框架强耦合具体网络栈

解法: 两个钩子, 用 designated init 留 NULL, XMODEM/YMODEM 自然不受影响:

```c
typedef struct {
    int (*begin)(...);
    int (*poll)(...);
    int (*end)(...);
    uint8_t (*progress)(...);
    int (*prepare)(ol_receiver_t *r, const void *arg);    /* 新增 */
} ol_receiver_ops_t;

typedef struct {
    int (*read)(...); int (*write)(...);
    int (*available)(...); int (*flush)(...);
    int (*connect)(ol_io_dev_t *dev, const char *host, uint16_t port);  /* 新增 */
    int (*disconnect)(ol_io_dev_t *dev);                                /* 新增 */
} ol_io_ops_t;
```

Updater 在 `url_or_null` 非 NULL 时调 `prepare(url)`. `cmd_update` 第 4 个参数承载 URL.

### 4.2 HTTP/1.0 receiver (commit `0e5cdfc`)

状态机:

```
IDLE         → 等 prepare/begin
PARSE_HEAD   → 逐字节按 \r\n 切行, 解析 status / Content-Length
RECV_BODY    → 流式 io->read → ol_part_write, 累计 == Content-Length 完成
DONE
```

- HTTP/1.0 + `Connection: close` (server 端尽快收尾, 不用处理 keep-alive)
- 仅支持 `Content-Length`, 不支持 `Transfer-Encoding: chunked`
- 状态码非 2xx 立即终止
- HTTPS 留 M3+ 接 TLS

### 4.3 IPD 段截断 bug (commit `be22f8c`)

**症状**: HTTP body 47468 字节, header 解析正常, 但 `body received` 始终不出现. body 流式阶段静默卡死.

**根因**: `port_esp_tcp_recv` 末尾有"吃尾"逻辑 — 单段 +IPD payload 超出 caller buf 的部分被 `port_uart2_read` 丢弃, 避免污染下一次 +IPD 解析. 而 `s_net.pending` 只有 1024 字节, ESP8266 单段 +IPD 受 TCP MSS 限制通常达 ~1460 字节 — **每段静默丢 ~436 字节**.

12d 阶段 `tcp test` 看到的 411/779 截断也是同一根因. 只是 M2-11 才把这个 bug 顶到表面.

**修复**: `s_net.pending` 从 1024 扩到 2048 (= port_uart2 ringbuf 同尺寸).

**教训**: smoke test 用 411 字节这种 < MSS 的小响应, 掩盖了 buffer 不足的问题. 需要用 ≥ 1500 字节的真实 payload 验证.

## 5. M2-13: 持久化日志 (oplog)

**commits**: `7d733a1` → `dd92ecb` → `01493a2`

### 5.1 格式与算法

固定 64B/slot, 在专属分区 (W25Q64 4KB sector × 4 = 16KB / 256 slots) 内环形写入.

```c
struct __attribute__((packed)) {
    uint32_t magic;     /* 0x474F4C4F "OLOG" */
    uint32_t seq;       /* 单调递增 */
    uint32_t ts_ms;     /* ol_tick_ms() at write */
    uint8_t  level;     /* 1=ERR 2=WRN */
    uint8_t  msg_len;   /* 实际 msg 字节数 */
    uint8_t  _pad[2];
    char     msg[44];   /* 截断, 不强制 null-term */
    uint32_t crc32;     /* 覆盖 [magic..msg] */
} oplog_rec_t;          /* sizeof == 64 */
```

启动时:
1. 扫描 256 slot, 找 `max(seq)` 且 CRC 通过的 slot
2. `write_idx = (max_idx + 1) % 256`, `next_seq = max_seq + 1`
3. 都为 erased 状态 → 新分区, `write_idx=0, next_seq=1`

Append 时若 `write_idx % SLOTS_PER_SECTOR == 0` 先 erase 该 sector (环形覆盖必须先擦回 0xFF 才能写下一轮).

Iter 找 `min(seq)` 的有效 slot 作为环形起点, 按物理顺序遍历到 `write_idx`. 物理顺序 == 时间顺序 (顺序 append + 环形覆盖).

### 5.2 Logger hook

`ol_vlog` 重构: 先用 `ol_vsnprintf` 得到裸消息, 再基于裸消息构造 console 输出 (色码 + `[E]` 前缀 + `\r\n`). 裸消息直接喂给 `ol_oplog_append`, dump 出来不带终端控制字符.

仅 ERR/WRN 入盘 — INFO 量大且 SPI flash 单次写 ~1ms, 自动持久化会拖慢启动. 显式持久化用 `ol_oplog_append`.

`s_in_progress` 防递归: hook 调 oplog → oplog 内部万一 LOGE → hook 再次触发 → in_progress=1 → silently drop.

### 5.3 端到端验收

```
oplog stat              → ready=1  used=0/256  write_idx=0  next_seq=1
jump nope               → [E] partition nope not found      (LOGE 触发 hook)
oplog stat              → used=1/256  next_seq=2
oplog dump              → 1 [E] 25026  partition nope not found
reset                   → 复位
oplog dump              → 仍可看到上一条 (持久化 OK)
update ymodem download app
^C (timeout)            → [E] receive failed: timeout
oplog dump              → 2 [E] 38954  receive failed: timeout (累积)
oplog clear             → ok
oplog stat              → used=0/256
```

## 7. 关键设计取舍回顾

| 取舍 | 选择 | 理由 |
|---|---|---|
| AT 层抽象 | 写死在 port 里, 不抽象 | 单板单 modem, 提早抽象增加心智负担 |
| HTTP/1.0 vs 1.1 | 1.0 + Connection: close | server 端简单, 无需 keep-alive 状态管理 |
| oplog 记录格式 | 固定 64B slot | 启动扫描简单, append O(1), bootloader 日志短文本足够 |
| oplog 自动入盘级别 | 仅 ERR/WRN | INFO 量大拖慢 SPI 写, 排查现场以错误为主 |
| AT v1.2 vs v2.x 兼容 | CIPMUX=0 单连接 | 单连接命令格式两版本一致, 不需分支 |
| receiver 接口扩展 | 新增可选钩子, designated init 留 NULL | 不破坏 XMODEM/YMODEM 现有接入 |
