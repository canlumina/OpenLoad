## 2. M5-1: F407VGT6 port

**commit**: `5c745f0`

### 2.1 为什么切 F4

F103 64KB bootloader 区在 M4 收尾已 74% 占用. M4-3 (dual bank) / M4-4
(HTTPS) 因平台硬伤压在 backlog. 选 F407VGT6:

| 维度 | F103ZET6 | F407VGT6 |
|---|---|---|
| Flash | 512KB (BL 区 64KB) | 1MB (BL 区可放宽到 256KB) |
| RAM | 64KB | 192KB |
| 内核 | Cortex-M3 @72MHz | Cortex-M4F @168MHz |
| Dual Bank | 无 | 硬件支持 (M5-1 不启) |
| FPU | 无 | 有 (M5-1 不启, M6+ 看需求) |
| 板载 SPI Flash | DevEBox 板载 W25Q16 (SPI1) | 板载 W25Q16 (SPI1) |

DevEBox MCUDev STM32F407 是手头现成板, 板载 W25Q16 直接复用 SPI Flash
路径; 后续 dual bank / HTTPS 验证不必换板.

### 2.2 ports/stm32f4 文件结构

跟 ports/stm32f1 对齐 (移植指南里说"5 步移植", 兑现):

```
ports/stm32f4/
├── include/
│   ├── port_stm32f4.h         # board 信息 + GPIO 宏
│   ├── port_uart2.h           # ESP8266 UART2
│   └── port_esp8266.h
└── src/                       # 1111 行 8 文件
    ├── board_init.c           #  41 行
    ├── port_button.c          #  27 行
    ├── port_flash_int.c       # 166 行  内部 flash (不均匀 sector)
    ├── port_flash_w25q16.c    # 141 行  外部 SPI Flash (M5-2 后收缩为 shim)
    ├── port_io_esp8266.c      # 349 行
    ├── port_io_uart.c         # 162 行
    ├── port_sys.c             # 101 行
    └── port_uart2.c           # 124 行
```

### 2.3 F4 特有适配 (跟 F1 差异点)

**内部 Flash 不均匀 sector lookup-table** — F1 是均匀 1K page, F4 是
4×16KB + 1×64KB + 7×128KB 共 12 个不均匀 sector (RM0090 §3.3). 不能像 F1
按固定 page size 公式算, 必须 lookup. `port_flash_int.c` 内嵌 sector 表
+ 智能批量擦 (一次 HAL_FLASHEx_Erase 跨多个 sector, 减少擦写命令开销).

**sys_jump 前清 CPACR** — F4 Cortex-M4F 带 FPU. bootloader 不启 FPU
(`-mfpu=none`), 但万一 app 启了 FPU 但 ResetHandler 跑到一半时 LR 里残留
bootloader 的 EXC_RETURN 用了 FP 上下文位 → 触发 NOCP UsageFault. 在
`sys_jump` 跳前显式 `SCB->CPACR &= ~((3UL<<20)|(3UL<<22))` 关 CP10/CP11,
让 app ResetHandler 在干净状态接管 (RM0090 §4.6.7). F1 没这问题.

**GPIO 显式 AF** — F1 走 AFIO REMAP (隐式), F4 每个 pin 单独设 AF (例:
SPI1 → AF5, USART1 → AF7). 显式后不会有"忘了 REMAP UART1" 类陷阱.

**DMA Stream + Channel 双索引** — F1 DMA1_Channel4 一维索引, F4 是
DMA2_Stream2_Channel4 两维 (RM0090 §10.3). 选 stream 错就触发不到, port
代码里硬编 stream/channel 对.

**SystemClock 168MHz** — `RCC_OscInitTypeDef`: PLL_M=8 (HSE 8MHz / 8=1MHz)
/ PLL_N=336 (1×336=336MHz) / PLL_P=2 (336/2=168MHz). `FLASH_LATENCY_5`
(168MHz 跨 5 个 wait state, RM0090 §3.5.1). 跟 F1 的 72MHz/2-WS 完全不同
计算式.

### 2.4 双工程切换

VSCode `tasks.json` + `inputs.pickString`: 用户在面板选 F1 / F4, task 调
对应 `examples/<board>/build/Debug` 路径. `openocd.cfg` 各 example 自带
一份, 烧录命令同 pattern.

### 2.5 端到端

烧测通过: boot → CLI → `info` (board_id 0x0407) → `part` 列 6 个分区 →
`oplog` 隐式证 W25Q16 read OK (SPI1 + PA15 CS 走通).

### 2.6 跟 F1 体积对比

`-Os` GCC 14.x, 全功能 (M1+M2+M3+M4 全 ON):

| 平台 | FLASH | RAM | BL 区 | 占用率 |
|---|---|---|---|---|
| F103ZET6 | 48.5 KB | 12.3 KB | 64 KB | 74.0% |
| F407VGT6 | 49.4 KB | 14.4 KB | 64 KB | 75.3% |

F4 略大原因: F4 startup + HAL 函数表略胖, Cortex-M4 Thumb-2 跟 M3 Thumb-2
指令编码差异极小 (M4 多了 DSP 指令但 -Os 用不到). RAM +2KB 是 HAL 缓冲
区差异. 仍同量级.

## 3. M5-2: W25QXX 通用驱动抽象

**commit**: `c819b1e`

### 3.1 抽象动机

F1 `port_flash_w25q64.c` (223 行) + F4 `port_flash_w25q16.c` (242 行) 总 465 行,
逐行 diff 99% 重复:

| 重复项 | F1 / F4 |
|---|---|
| W25Q 命令字 (0x06/0x05/0x03/0x02/0x20/0xAB/0x9F) | 完全相同 |
| wait_busy / write_enable / 状态机 | 完全相同 |
| `w25_read` / `w25_write_page` / `w25_write` / `w25_erase` ops | 完全相同 |
| 初始化流程 (SPI init → RELEASE_PD → JEDEC) | 完全相同 |
| SPI 后端 (端口 / CS pin / AF / 分频 / MspInit) | 不同 |
| chip 参数 (size / JEDEC ID / name) | 不同 (16Mb vs 64Mb) |

接第三颗 W25Q* 等于再复制一遍. M5-1 双平台并存让重复成了 reality, 必须抽.

### 3.2 抽象边界

**driver (chip-agnostic)**: 命令字 + 状态机 + ops + chip_init 流程
**port (chip-specific)**: SPI/GPIO 后端 + chip 参数

driver 不知道具体 SPI/GPIO 怎么调, port 通过 `w25qxx_config_t` 注入 6 个
后端函数 + 3 个 chip 参数:

```c
typedef struct {
    const char *name;
    uint32_t    size;
    uint32_t    expected_jedec;
    int     (*spi_init)(void);
    uint8_t (*spi_xfer)(uint8_t b);
    void    (*spi_write)(const uint8_t *p, uint32_t n);
    void    (*spi_read)(uint8_t *p, uint32_t n);
    void    (*cs_low)(void);
    void    (*cs_high)(void);
} w25qxx_config_t;
```

### 3.3 ops 拿 cfg 的路径: `dev->priv`

通用 driver 不能持 static cfg (会卡多 chip 多实例). 解: `ol_flash_dev_t.priv`
存 `w25qxx_config_t *`, ops 函数签名第一个参数本就是 `ol_flash_dev_t *`,
直接 `(const w25qxx_config_t *)dev->priv` 取后端. 同一份 `w25qxx_ops` 静态
实例能服务任意多颗 chip (port 各自声明独立 dev/cfg 即可).

### 3.4 时间抽象

`wait_busy` 改用 `ol_tick_ms()` 而非 `HAL_GetTick()`, `w25qxx_chip_init`
改 `ol_delay_ms()` 而非 `HAL_Delay()`. 通用 driver 跨 HAL 平台干净 — F1
HAL / F4 HAL / 未来 Linux mmap / 单元测试 mock 都能直接接.

### 3.5 顺手加严 JEDEC ID 校验

抽象前: 仅检查 `id != 0 && id != 0xFFFFFF` (避 SPI 全 0/全 F 噪声). 期望
JEDEC ID 写在注释里没比对 — 接错 chip 也不报.

抽象后: `cfg->expected_jedec` 严匹配, 不一致直接 `OL_E_IO`:

```c
if (id == 0 || id == 0xFFFFFFu) { return OL_E_IO; }
if (cfg->expected_jedec != 0 && id != cfg->expected_jedec) { return OL_E_IO; }
```

`expected_jedec = 0` 仍兼容"不严校验"模式 (例: 同 driver 接未知 W25Q* 调试时).

### 3.6 文件结构

| 文件 | 类型 | 行数 |
|---|---|---|
| `openload/include/openload/devices/w25qxx.h` | 新, 接口 | 55 |
| `openload/devices/w25qxx.c` | 新, 通用 driver | 151 |
| `ports/stm32f4/src/port_flash_w25q16.c` | 重写为 shim | 141 (-101) |
| `ports/stm32f1/src/port_flash_w25q64.c` | 重写为 shim | 128 (-95) |

净行数: 抽象前 465, 抽象后 (151 + 141 + 128) = 420 行, **减 45 行**. 但
更重要的是: 接第三颗 chip 只需 ~120 行 shim (+ 一行 cfg 配置), 不动 driver.

### 3.7 体积验证

F4 `-Os` 全功能:

| 阶段 | FLASH | 增量 |
|---|---|---|
| 抽象前 (M5-1) | 49352 B | (基准) |
| 抽象后 (M5-2) | 49352 B | **+0 B** |

函数指针 indirection 跟宏直接调用差别极小, `-Os` + `gc-sections` 抹平.
0 字节代价, 复用度大涨.

### 3.8 端到端

F4 板回归通过: `oplog: 28/256 used` 历史数据无损读出 (证实 SPI read +
状态机正确) + `erase wifi_cfg` round-trip OK (写擦链路正确) + JEDEC
严校验真实命中 0xEF4015 (板载 W25Q16 确认).

F1 板回归 deferred — 用户决定 F4 主线先全跑完再回头.

## 4. M5-3: examples/common/

**commit**: `57b14d5`

### 4.1 抽象动机

F1/F4 example 各自持 `partitions.c` / `commands.c` / `wifi_cfg.{c,h}` 共 4
文件:

| 文件 | 行数 | F1 vs F4 |
|---|---|---|
| `partitions.c` | 19 | byte-identical |
| `commands.c` | 315 | byte-identical |
| `wifi_cfg.c` | 78 | 仅注释 1 行差 (W25Q16 / W25Q64) |
| `wifi_cfg.h` | 21 | 仅注释 1 行差 |

跟 M5-2 性质一样, 是 example 业务层的重复. 抽得也直接.

### 4.2 抽象边界

`examples/common/` 放 chip/board-agnostic 业务源, example 根目录仅留
chip/board-specific 配置:

- **commin/** (共享): `partitions.c` / `commands.c` / `wifi_cfg.{c,h}`
- **example 根** (各自): `partitions.def` (分区表, 跟 board flash 容量绑)
   + `openload_config.h` (启用哪些功能)
   + `linker.ld` (跟 chip 内存映射绑)
   + `Core/Inc`+`Core/Src` (HAL Init / IT / 系统时钟)

### 4.3 partitions.c 在 common 怎么找 partitions.def

`partitions.c` 用 X-macro 展开:

```c
static const ol_partition_t g_partitions[] = {
#define OL_PART(_dev, _name, _off, _sz, _fl) ...
#include "partitions.def"           // <-- 这里
#undef OL_PART
};
```

`partitions.c` 搬到 `examples/common/` 后, 双引号 include 先从 source
文件同目录 (common/) 找 `partitions.def` — common/ 里没有, **fallback 到
-I path**. 各 example `CMakeLists.txt` `target_include_directories PRIVATE
${CMAKE_SOURCE_DIR}` 把 example 根加进 -I, fallback 正好命中.

设计为本: **业务源跨 example 共享, 配置仍各自持有**. 不同 board 的分区
表是固有差异, 不该让 common/ 知道.

### 4.4 wifi_cfg 注释中性化

`wifi_cfg.{c,h}` 头注释原来写 "W25Q16 上 wifi_cfg 分区" / "不直接依赖
W25Q16 驱动". 搬到 common/ 后要么写 W25Q16/Q64 双方都不对, 要么改中性:

```diff
- WiFi 凭据持久化 (W25Q16 上 wifi_cfg 分区)
+ WiFi 凭据持久化 (外部 SPI Flash 上 wifi_cfg 分区)

- 走 OpenLoad partition API, 不直接依赖 W25Q16 驱动 ...
+ 走 OpenLoad partition API, 不直接依赖具体 flash 驱动 ...
```

避免 chip 字面在共享代码里复活.

### 4.5 体积验证

| 平台 | 抽象前 | 抽象后 |
|---|---|---|
| F4 | 49352 B | 49352 B |
| F1 | 48496 B | 48496 B |

纯物理搬家, 0 字节代价.

## 5. M5-4: 删 legacy/ 76MB + F1 自包含化

**commit**: `dfadba4`

### 5.1 legacy/ 是什么

M0 阶段 (新框架重写之前) 的旧 Keil/GCC 工程 + 旧 vendor HAL + 早期开发
计划:

```
legacy/ (76MB, 1159 tracked files)
├── docs/
│   ├── STM32F407VX_M_schematics.pdf      298KB  F4 板原理图 (要救)
│   └── bootloader_development_plan.md      4KB  M0 前的计划 (已被 M1-M5 历史覆盖)
└── example/
    ├── gcc/                              69MB   旧 GCC 工程 + HAL vendor
    ├── platform/                        7.1MB   旧 HAL vendor (CMSIS + STM32F1xx)
    └── keil/                             310KB  旧 Keil 工程
```

新框架 (openload/ + ports/ + examples/) 已经把 v0 全部内容覆盖, legacy/
仅作 v0 → 新框架迁移期间的对照参考. M5-4 是清空它的时候.

### 5.2 F1 工程对 legacy/ 的隐性依赖

勘探时发现一个潜伏问题: F1 `examples/stm32f103zet6_gcc/cmake/stm32cubemx/
CMakeLists.txt` 拉 HAL/CMSIS 走的是 `${CMAKE_SOURCE_DIR}/../../legacy/
example/gcc/Drivers/` — 整个 12 个 HAL .c + 全套 CMSIS 头都从 legacy/
取. **直接删 legacy/ 会立刻断 F1 编译**.

F4 (M5-1) 当时就走的自包含路径 (`examples/stm32f407vgt6_gcc/Drivers/`
本地放 HAL), F1 还停在 M1 的过渡形态.

### 5.3 解法: F1 跟 F4 对齐自包含

复制 `legacy/example/gcc/Drivers/{STM32F1xx_HAL_Driver,CMSIS}` 到
`examples/stm32f103zet6_gcc/Drivers/`, 改 F1 stm32cubemx CMakeLists 指本地:

```diff
- # legacy 中 HAL 库的绝对路径
- set(LEGACY_GCC_ROOT "${CMAKE_SOURCE_DIR}/../../legacy/example/gcc")
- set(HAL_DRV         "${LEGACY_GCC_ROOT}/Drivers/STM32F1xx_HAL_Driver")
- set(CMSIS           "${LEGACY_GCC_ROOT}/Drivers/CMSIS")
+ set(DRIVERS_ROOT "${CMAKE_SOURCE_DIR}/Drivers")
+ set(HAL_DRV      "${DRIVERS_ROOT}/STM32F1xx_HAL_Driver")
+ set(CMSIS        "${DRIVERS_ROOT}/CMSIS")
```

完事后 legacy/ 才能安全删. git rename detection 把绝大多数 vendor 文件
识别为 rename (内容 100% 一致), 实际 diff 极小.

### 5.4 物理变更

| 动作 | 路径 |
|---|---|
| 挪 | `legacy/docs/STM32F407VX_M_schematics.pdf` → `docs/board/` |
| 删 | `legacy/docs/bootloader_development_plan.md` (M0 计划, 历史已覆盖) |
| 删 | `legacy/example/{gcc,keil,platform}/` 整 76MB |
| cp + git rename | F1 HAL/CMSIS 从 legacy/ → `examples/stm32f103zet6_gcc/Drivers/` |
| 改路径 | F1 `stm32cubemx/CMakeLists.txt` 改本地 Drivers/ |
| 清引用 | `README.md` / `docs/spec/ARCHITECTURE.md` / F1 `README.md` 4 处 |

### 5.5 验证

- F1 重 build: `cmake --build build/Debug` → **FLASH 48496 B, 跟脱钩前
  c819b1e 字节相同** (纯路径切换, vendor 内容相同, 不影响任何产物).
- F1 删 legacy/ 后再 build: `ninja: no work to do` (零残留依赖确认).
- 全仓 grep `legacy/` 仅命中 HAL 自带 "legacy weak callback" 注释 (HAL

## 7. 关键设计取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| 平台扩展方向 | F407VGT6 | DevEBox 板手头有, 板载 W25Q16 复用 SPI 路径; M6+ dual bank/HTTPS 不必换板 |
| F4 FPU | bootloader 不启 (sys_jump 前清 CPACR 防 app 副作用) | bootloader 用不上, 启了多 startup 开销; app 自由启 |
| W25QXX driver 放哪 | `openload/devices/w25qxx.c`, 跟 core/crypto/proto 平级 | 跨 port 共享; 不算"硬件",  framework 概念上一颗 chip 抽象 |
| W25QXX ops 拿 cfg | 走 `dev->priv` 取 `w25qxx_config_t *` | 静态全局只能服务一颗 chip; priv 走通后支持任意多实例 |
| W25QXX 时间 API | `ol_tick_ms` / `ol_delay_ms` (不直接 HAL) | 跨平台 driver 不该耦合 HAL_GetTick |
| JEDEC ID 校验 | 严匹配 `cfg.expected_jedec` (0 跳过严匹配) | 接错 chip 早爆; 例工程仍能用 0 调试未知 chip |
| common/ 范围 | 业务源 (partitions.c/commands.c/wifi_cfg.{c,h}) | 这些 F1/F4 已 byte-identical (wifi_cfg 仅注释字面差) |
| common/ 不包括 | partitions.def / openload_config.h / linker.ld / Core/* | board/chip 特定配置, 共享会出错 |

| F1 HAL 处理 | 跟 F4 对齐自包含 (复制到本地 Drivers/) | 仓库自洽, clone 即编, 不绑外部路径 |

## 10. M5 阶段意义

M5 不引入新功能, 是一次"工程层结构化". 关键成果:

1. **双平台并存** — F1 (M1-M4 验证主力) + F4 (M6+ 扩展基线), bootloader
   不再绑死单芯片.
2. **抽象代价为 0** — 体积零变化前提下, 接新 W25Q* / 新 board / 新 chip
   边际成本从"复制 + 改"降到"加 cfg + 写 shim".
3. **仓库自洽** — 删 76MB legacy 历史包袱, F1 跟 F4 都自包含, 没有外部
   路径依赖, clone 即编.
4. **覆盖 backlog 准备** — M4 转过来的 dual bank / HTTPS 在 F4 上能直接
   做了, M6 开工不必先解决平台.
