## 3. M6-1: RDP 软件控制 (L0→L1)

**commit**: `9600f0a`

### 3.1 为什么做这个

M4-2 落完 Ed25519, 安全栈表面闭环: 设备只接受用私钥签过的 image. 但
**公钥编在 bootloader bin 里**. 攻击者:

1. SWD 接上设备, `STM32_Programmer_CLI` dump 整个 bootloader flash
2. 找到 `g_ed25519_pubkey[32]` 偏移
3. 改成自己私钥对应的公钥
4. 写回设备 → 之后用攻击者私钥签的恶意 image 通过校验

**M4 安全栈的根 (公钥) 不在硬件保护下, 等于没用**.

STM32 RDP (RM0090 §3.6) 是 ST 给的硬件答案:

| Level | 含义 | 可逆? |
|---|---|---|
| L0 (0xAA) | 出厂默认, SWD 全开 | — |
| L1 (其他值) | SWD 锁读 flash + RAM SRAM2; 可调试 SRAM 但读不到 flash | ✅ 可解锁 (触发 mass erase) |
| L2 (0xCC) | 完全封, debug 永久关闭, **不可逆** | ❌ |

M6-1 把 **L0→L1 软件控制**打通. L2 不进 CLI — 误触代价是整片板报废,
production 最后一步走 ST_LINK 外部工具显式烧.

### 3.2 sys_ops 扩展

`ol_sys_ops_t` 加 2 可选 op (跟 `magic_read`/`magic_write` 同模式 — port
不提供就返 `OL_E_NOT_SUPPORTED`):

```c
int (*rdp_get_level)(uint8_t *out);   /* 返回 OL_RDP_LEVEL_NONE/READ_PROT/FULL */
int (*rdp_lock)(void);                /* 触发 L0→L1, 通常立即复位不返回 */
```

加 3 个 level 宏 `OL_RDP_LEVEL_{NONE,READ_PROT,FULL}` (跟 ST `OB_RDP_LEVEL_*`
不直接绑, port 内做翻译, 框架不知道 STM32 具体编码).

`openload/core/sys.c` 加 `ol_rdp_get` / `ol_rdp_lock` wrapper, port 未注册
返 `OL_E_NOT_SUPPORTED`. F1 端 sys_ops 这两字段 = NULL, **designated
initializer 完全兼容**, F1 CLI `rdp` 直接吐 "not supported on this port",
不挂.

### 3.3 F4 port_rdp.c 实现要点 (78 行)

**get 不解锁 flash** — `HAL_FLASHEx_OBGetConfig` 只读 option byte 寄存器,
不需要 OB_Unlock. 安全侧只查询不该修改.

**lock 硬约束 L0→L1** — 函数开头先 `get_level`, 不是 `LEVEL_NONE` 直接
返 `OL_E_INVAL`. L1→L1 无意义, L1/L2 升 L1 不存在, 都拒. 防误操作.

**OB 写流程** (RM0090 §3.6.2): `HAL_FLASH_Unlock` → `HAL_FLASH_OB_Unlock`
→ `HAL_FLASHEx_OBProgram(RDP=L1)` → `HAL_FLASH_OB_Launch`. Launch 触发
option byte reload, F4 通常立即 BOR 复位**不返回**.

**OB_Launch 不返回不是 RM 强保证** — 极少数情况能跑回来 (例: 写入失败但
HAL_OK 返回). 防御性把后半段 `OB_Lock + FLASH_Lock` 写满, 让 CLI 能正常
打印 "lock issued, manually reboot to apply" 而非死机.

### 3.4 CLI `rdp` 命令组

| 子命令 | 行为 |
|---|---|
| `rdp` / `rdp status` | 显示当前 level + 含义 ("unlocked" / "read-protected" / "FULL permanent") |
| `rdp lock` | 触发 L0→L1, 带 **10s 倒计时 + 'y' 二次确认 + 解锁命令文档化** |
| `rdp unlock` | **不存在** — 解锁意味着 mass erase, 走外部工具更直白 |
| `rdp l2` | **不存在** — 永久不可逆, 不该藏在 CLI 里 |

不暴露 `unlock` / `set` / `l2` 是设计选择. CLI 给的能力 = 误触代价可控
的范围, 超出范围让用户走 `STM32_Programmer_CLI -c port=SWD -ob RDP=0xAA`,
后者命令字面清楚, 不会被 tab 补全误触发.

### 3.5 体积

| 平台 | M5 收尾 | M6-1 后 | 增量 |
|---|---|---|---|
| F4 (RDP ON) | 49352 B | 51628 B | **+2276 B** (HAL_FLASHEx_OB* 全家拉入) |
| F1 (RDP OFF) | 48496 B | 48504 B | **+8 B** (仅 sys_ops 结构体扩展 .rodata) |

F4 +2.3KB 不算便宜 — HAL `OBProgram` 拉了一堆 OB 相关函数 (sector
protection / WRP / SPRMOD / ...) 即使 OpenLoad 只用 RDP 字段. 用 `-Os` +
`gc-sections` 已经撕过一遍, 残留这么多是 HAL 内部互相调用导致的. F4 64KB
BL 区现在 78.8% (Debug), 还有 14KB 余量, 跑.

F1 +8B 因为 sys_ops 多了 2 个 NULL 函数指针 + 翻译宏, 几乎零代价.

## 4. M6-2: 多 board_id 支持

**commit**: `83507c5`

### 4.1 为什么做

`OPENLOAD_BOARD_ID` 是 image 头里的 16-bit 字段, 防止 F1 板的 image 误刷
到 F4 板. 之前 image 头里**只有 1 个**, 量产 N 个 SKU 共用 firmware 时
要给每个 SKU 单独打 image (改 board_id 重打), 工具链/分发都麻烦.

跑业务时这事在 PR #1 讨论里冒出来 — "我有 F103 跟 F407 两个板, 同一份
App 源码, 但 image_tool 出来的 image 板间不通". 改 image hdr 支持多
board_id 就行, 但要**向后兼容老 image**.

### 4.2 hdr 扩展: 不动 size 不 bump version

ol_image_header_t 64B 固定, 其中 v2 时代预留了 `reserved[4]` 给 Ed25519
签名做 hdr 内扩展用. 实际 M4-2 Ed25519 落地时签名走 **image trailer**
(payload 末尾 64 字节) 不占 hdr, `reserved[4]` 一直闲着.

M6-2 把这 4 字节转作 `board_id_extra[2]` (2 个 uint16):

```c
typedef struct {
    /* ... 前面字段不动 ... */
    uint16_t board_id;            /* 主槽 (一直存在) */
    /* ... 中间字段不动 ... */
    uint16_t board_id_extra[2];   /* M6-2 新增: 额外 2 槽 (M6 之前是 reserved[4]) */
    uint32_t hdr_crc32;
} __attribute__((packed)) ol_image_header_t;
```

- hdr 仍 64B (`_Static_assert` pass)
- `OL_IMAGE_FMT_VER` 不 bump (没 ABI 破坏)
- 老 image (extra 全 0 来自 reserved=0): 设备读出 extra=(0,0), 等同单板

### 4.3 verify 改 3 槽循环

`openload/core/image.c` 校验逻辑从单值比对改 3 槽循环:

```c
uint16_t slots[3] = { hdr.board_id, hdr.board_id_extra[0], hdr.board_id_extra[1] };
bool matched = false;
for (int i = 0; i < 3; ++i) {
    if (slots[i] != 0 && slots[i] == OPENLOAD_BOARD_ID) {
        matched = true; break;
    }
}
if (!matched) { return OL_E_IMAGE_BOARD; }
```

**0 = unused 哨兵, 不参与匹配**. 假设设备的 `OPENLOAD_BOARD_ID=0` (用户
没配置), 任何 slot 跟 0 不该匹配 — 这条 if 顺手挡了配置缺失的 image
意外通过.

### 4.4 image_tool --board-id 多值

```bash
# 单值 (兼容 M1)
python tools/image_tool.py app.bin --board-id 0x0103 -o app-ol.bin

# 多值 (M6-2 新增, 逗号分隔, 最多 3 个)
python tools/image_tool.py app.bin --board-id 0x0103,0x0407 -o app-ol.bin
python tools/image_tool.py app.bin --board-id 0x0103,0x0500,0x0407 -o app-ol.bin
```

struct.pack 把 3 个 uint16 写到原 reserved 4B 位置 (1 主 + 2 extra). 不足
3 个的槽填 0 (= unused).

image_tool 6 case 自检全过 (commit body 列了):
- 单值 / 双值 / 三值 列槽位
- 跨板 0 → 0x0000 (cross-board 占位)
- 超 3 个 → "error: max 3 board_ids supported"
- 超 u16 → "error: out of u16 range"

### 4.5 体积

| 平台 | M6-1 收尾 | M6-2 后 | 增量 |
|---|---|---|---|
| F4 | 51628 B | 51676 B | **+48 B** (3 槽 array init + for loop) |
| F1 | 48504 B | 48552 B | **+48 B** (同上) |

行为差异极小, +48B 就是循环展开成本.

## 5. M6-3: ESP UART2 波特率抽宏

**commit**: `b6e71a6` (PR #2, fix #1)

### 5.1 现象

我的 F4 板插的是 ESP-01 老固件 (AT v0.x, default baud 9600). F4 代码
里 UART2 (连 ESP8266) **硬编码 115200**. `esp ping` 立即 timeout, 完全
握不上 AT 通道.

### 5.2 不仅 1 处硬编码

grep 出来 4 个地方写 115200, **两条独立路径**:

| 位置 | 作用 |
|---|---|
| `ports/{stm32f1,stm32f4}/src/port_uart2.c` | `port_uart2_init(115200)` 默认值 |
| `examples/{stm32f1,stm32f4}/Core/Src/usart.c` | `MX_USART2_UART_Init` 里 `huart2.Init.BaudRate=115200` |

CubeMX 生成的 `usart.c` 跟 OpenLoad port 的 init 各自拿了个 115200,
**两份不一致也能编过** (HAL 后写的覆盖前写的). 之前出过 "代码字面
115200 但实际跑 9600" 的诡异歧义, 就是这两路径不同步.

### 5.3 单一 source of truth

抽 `OPENLOAD_ESP_UART_BAUD` 配置宏, 4 个地方都读它:

```c
/* openload/include/openload/config_default.h */
#ifndef OPENLOAD_ESP_UART_BAUD
#define OPENLOAD_ESP_UART_BAUD 115200   /* 跟 fix 前一致, 不破坏现有用户 */
#endif
```

```c
/* F4 examples/.../openload_config.h */
#define OPENLOAD_ESP_UART_BAUD 9600     /* 我的 ESP-01 老固件 */
```

```c
/* ports/.../board_init.c */
port_uart2_init(OPENLOAD_ESP_UART_BAUD);

/* examples/.../Core/Src/usart.c */
huart2.Init.BaudRate = OPENLOAD_ESP_UART_BAUD;
```

默认 115200 = 跟 fix 前字面一致, 不动现有用户. F4 example **显式 9600**
是因为我手上模块需要; 别人不需要可以删. 用户改 baud 改 1 个宏, 4 个
.o 文件全跟上.

### 5.4 GitHub 流程

这条改动走 PR 流程 (Issue #1 报问题 → PR #2 修, 关闭 #1). 是这个项目第
一次走"issue → PR → merge"完整 GH 流程. squash merge 合到 main, 删
branch, 没问题.

## 6.5 M6-5: GitHub Actions 编译矩阵

**commits**: `<a>` (build: OPENLOAD_CI_MINIMAL 选项) + `<b>` (ci: workflow + docs)

### 6.5.1 为什么做

M3 路线图就挂了 "CI 编译矩阵" 这一笔, 一直没动. 当前回归靠手工:
每改一处, 我自己跑 `cmake --build` 两个 example 两种 buildtype. M5+M6
累积下来 F1 路径 deferred 多次, 实板烧测延后, 编译期 regression 也只能
靠肉眼盯 log.

CI 的核心价值:
1. **PR / push 自动 catch 编译 regression** — 8 个 build path 任何一个
   挂都立刻可见, 阻 PR 合并.
2. **验证 #ifdef 裁剪正确性** — 加 "minimal config" 变体 (只启 M1:
   XMODEM + CRC32 + CLI), 防止 "关掉某特性后链接挂" 这类隐患. 是框架
   "可裁剪" 卖点的强保证.
3. **README 体积参考自动更新** — 每次 push 出体积表 (写到
   `$GITHUB_STEP_SUMMARY`), 不再靠手工数.

### 6.5.2 矩阵设计

2 board × 2 buildtype × 2 variant = **8 jobs**, 全并行, ubuntu-latest
runner, 总墙钟时间 ~5min.

| board | buildtype | variant |
|---|---|---|
| F1 (stm32f103zet6_gcc) | Debug | full / minimal |
| F1 | Release | full / minimal |
| F4 (stm32f407vgt6_gcc) | Debug | full / minimal |
| F4 | Release | full / minimal |

- **GCC pin 14.2.Rel1** via `carlosperate/arm-none-eabi-gcc-action@v1`
  (本地用 15.2.1, CI 锁 14.2 这条公认稳定线, 防 GCC 升级引入 regression)
- `fail-fast: false` — 一个 cell 挂不影响其他, 看完整结果
- `paths-ignore: docs/** + **.md` — 改 README/devlog 不触发 CI (省额度)
- `cancel-in-progress` 仅 PR 启用, push 到 main 不取消保留历次状态

### 6.5.3 "minimal" 配置定义

只启 M1 默认 (XMODEM + XMODEM-1K + CLI + CRC32), 关闭 M2-M6 所有特性
(YMODEM / HTTP_OTA / OPLOG / ESP8266 / AES / SHA / Ed25519 / RDP /
anti-rollback / backup). 是框架"裁剪到最小"的极限场景, 体积应回到
M1 默认量级.

### 6.5.4 "shadow include" 架构

example 的 `openload_config.h` 是 user-authored, 硬编码启用 M2-M6 +
AES key + Ed25519 pubkey. CI 切 minimal 不能原地改这个文件 (污染主分支).

方案: example 下加 `ci_minimal/openload_config.h`, 内含 M1-only 配置.
CMake 在 `OPENLOAD_CI_MINIMAL=ON` 时把这个子目录加到 openload target
的 include path **并 BEFORE** (shadow 主目录), 框架的
`__has_include("openload_config.h")` 找到 minimal 那份, **不动其他任何
代码**.

```cmake
option(OPENLOAD_CI_MINIMAL "..." OFF)

if(NOT OPENLOAD_CI_MINIMAL)
    set(OPENLOAD_ENABLE_YMODEM ON CACHE BOOL "..." FORCE)
    # ... 其他 M2-M6 cache vars
endif()

if(OPENLOAD_CI_MINIMAL)
    target_include_directories(openload BEFORE PUBLIC
        ${CMAKE_SOURCE_DIR}/ci_minimal)
else()
    target_include_directories(openload PUBLIC ${CMAKE_SOURCE_DIR})
endif()
```

### 6.5.5 踩到的坑: exe target 的 include 不继承 openload 库的 BEFORE

**第一遍跑 F1 Release minimal 时, link 挂在 `cmd_tcp` 引用未定义符号
`port_esp_tcp_close`**. 但 `commands.c` 里 `cmd_tcp` 是 `#if
OPENLOAD_ENABLE_ESP8266` 包着的, minimal 配置该宏=0, 应该整段不编入.

原因: `commands.c` 是在 `${PROJECT_NAME}` (exe) 目标里编, 不是 openload
库目标. exe 的 include 解析顺序里, 它自己 PRIVATE 的 `${CMAKE_SOURCE_DIR}`
排在前面, **库 PUBLIC 继承下来的 ci_minimal BEFORE 排在后面**. 所以
commands.c TU 经过 `#include "openload/config.h"` → `__has_include
("openload_config.h")` 时, 仍找到主目录的 `openload_config.h` (ESP8266=1),
`cmd_tcp` 被编入, 链接挂.

修法: exe target 自己也加一个 conditional BEFORE include:

```cmake
if(OPENLOAD_CI_MINIMAL)
    target_include_directories(${PROJECT_NAME} BEFORE PRIVATE
        ${CMAKE_SOURCE_DIR}/ci_minimal
    )
endif()
```

这个坑值得记下来: 框架的 `__has_include` 风格配置加载, 跟 CMake 库目标
include 继承顺序有微妙交互, 任何**不在 openload 库内部编译**的源 (user
工程、common 助手) 如果也 `#include "openload/config.h"` 就会踩到.
shadow 不是一行 `target_include_directories(openload BEFORE)` 能搞定的,
要给所有"会读 openload_config.h" 的目标都 BEFORE 一遍.

### 6.5.6 warning-as-error 走 grep 不走 -Werror

ARM HAL 偶有 GCC 警告不可控 (CubeMX 生成的代码里有些 implicit
fallthrough / unused parameter), 全局 `-Werror` 会把它们升 error 阻 CI.
取舍: warning-as-error 走 build log 的 `grep -E "warning:|error:"`,
精确控制范围 (CMake 自己输出的 "WARN" 不带冒号不会误触).

第一版先按这方案, 误报再加规则 (如 `grep -v "CubeMX:"` 排除特定行).

## 8. 关键设计取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| RDP L2 是否进 CLI | **不进** | 永久不可逆, 误触整板报废. 走 ST_LINK 外部工具显式烧, 命令字面清楚不会 tab 补全误触发. |
| RDP unlock 是否进 CLI | **不进** | 解锁 = mass erase, "在 bootloader CLI 里抹掉 bootloader 自己" 逻辑混乱. 用户走 `STM32_Programmer_CLI -ob RDP=0xAA` 直白. |
| RDP lock 二次确认 | **10s + 'y'** | 锁了之后丢调试通路, 跟 sudo rm -rf 一个量级. 让用户有 10s 反悔机会. |
| F1 RDP 这次做不做 | **不做** | F4 路径走通即可证明设计, F1 HAL `OB_*` 跟 F4 极其相似但函数名略不同 (`HAL_FLASHEx_OBProgram` 在 F1 是 `HAL_FLASHEx_OBProgram` + sector-erase 路径), 单独 M7 一条收尾 commit 更清晰. |
| OB_Launch 不返回的兜底 | **写满 lock/relock 路径** | RM 没强保证 Launch 立即复位, 让 CLI 能 print "manually reboot" 而非死机, 给用户调试余地. |
| image hdr 扩 board_id 是 bump version 还是复用 reserved | **复用 reserved** | hdr 仍 64B, FMT_VER 不动, 老 image (reserved=0) extra=(0,0) 行为同 M1 单板. 干净的向后兼容. |
| 0 = unused 哨兵 | **是** | 跟 "OPENLOAD_BOARD_ID=0 (用户没配)" 默认值天然不匹配, 顺手挡未配置的 image 意外通过. |
| 多 board_id 上限 | **3 槽** | reserved 只有 4 字节 = 2 个 uint16, 加上主槽 = 3. 量产 SKU 数量 3 个内常见, 超过应该考虑 image signing infrastructure 分发不同 image. |
| image_tool 多值 syntax | **逗号分隔** | shell 不需要 quote, 不跟其他 `--xxx=` 风格冲突. |
| ESP baud 抽宏默认值 | **115200** | 跟 fix 前字面一致, 不破坏现有用户. 用户拿老固件 ESP-01 自己 override 9600. |
| baud 宏读取点 | **board_init.c + usart.c 都读同一宏** | 历史上"代码字面 X 但实际跑 Y" 的歧义就是两路径不同步导致, 抽宏后单一 source of truth. |
| host_test 程序补 commit | **保留** | 切 crypto 实现 (mbedtls / micro-ecc) 时回归对拍用, 留 100 行代码值得. |

## 11. M6 阶段意义

M6 (Part 1) 是个"收口里程碑", 不引入大块新功能:

1. **闭合 M4 安全栈最后一环** — RDP L1 锁住 bootloader 的 SWD 读路径,
   pubkey/AES key 不再裸露. M4 的 Ed25519 签名校验从此**真的有意义**.
2. **量产路径打通** — 多 board_id 让一份 firmware + image 覆盖多 SKU,
   不必给每板单独打 image.
3. **PR/Issue 流程跑通** — Issue #1 → PR #2 → squash merge 走完一轮,
   后续社区贡献流程可参考.
4. **F1 路径不再 deferred** — M5+M6 累积改动在 F1 编译干净, 编译阶段
   不再积累风险 (实板烧测仍待确认).
5. **编译回归机械化** — 8-job CI 矩阵 (F1/F4 × Debug/Release × full/minimal)
   把以前手工编验证彻底自动化, 顺手挖出 "shadow include 仅对 openload
   库 TU 生效" 的隐藏坑.
